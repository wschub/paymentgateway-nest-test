# Phase 1 Data Model: Finalize Checkout — Summary, Payment, Final Status and Refresh Recovery

**Feature**: `005-finalize-checkout` | **Date**: 2026-10-14

This feature adds **no database table** and changes **no persisted schema**: the back-end entities
(Transaction, Delivery, Customer, Product) are unchanged and defined in
`specs/002-transacciones-pagos/data-model.md`, and the persisted checkout document stays the version-2
whitelist from `specs/003-front-end-store/contracts/persistence.md`. This document models the **front-end**
entities this feature consumes and the recovery lifecycle it adds. Card number, CVC and card token have
**no field** anywhere below (the token lives only in `CheckoutModal` component memory).

## API entity: TransactionView (read model, source of truth for status)

Consumed as typed in `features/checkout/checkout.types.ts` against the contract
[`specs/002-transacciones-pagos/contracts/rest-api.md`](../002-transacciones-pagos/contracts/rest-api.md).
Two shapes exist; the front-end types them separately.

### `TransactionCreated` — `POST /transactions` (201 Created / 200 idempotent replay)

| Field | Type | Rules |
|-------|------|-------|
| `id` | string | purchase id; persisted as `transactionId` |
| `reference` | string | unique server reference, `TXN-` + 16 characters; server-generated, shown to the shopper verbatim (never client-constructed or validated beyond display) |
| `status` | `TransactionStatus` | always `PENDING` on creation |
| `quantity` | integer | `1..10`; server clamps/validates; client mirrors `MAX_QUANTITY_PER_PURCHASE` |
| `amounts.productAmountInCents` | integer | `priceInCents × quantity`, server-computed |
| `amounts.baseFeeInCents` | integer | server configuration |
| `amounts.deliveryFeeInCents` | integer | server configuration |
| `amounts.totalInCents` | integer | sum, server-computed |

`TransactionCreated = Omit<TransactionView, 'card' | 'product' | 'delivery' | 'failureReason'>` — the
enrichment never appears here. The summary renders these five groups **verbatim** (FR-003, SC-001).

### `TransactionView` — `POST /transactions/:id/payment` (202 / 200) and `GET /transactions/:id` (200)

The five creation fields **plus** the optional enrichment. Every enrichment read is guarded (optional
chaining + fallback to the selected product and the delivery form).

| Field | Type | Rules |
|-------|------|-------|
| *(creation fields above)* | | identical to `TransactionCreated` |
| `card` | `TransactionCard \| null` (optional) | `{ brand, lastFour, installments }` — display only |
| `product` | `TransactionProduct \| null` (optional) | `{ id, name, quantity }` |
| `delivery` | `TransactionDeliveryView \| null` (optional) | `{ status, address, city, region }`; status `ASSIGNED` only when approved |
| `failureReason` | `string \| null` (optional) | safe reason, e.g. `RESERVATION_EXPIRED` |

Supporting enums/types:

- `TransactionStatus = 'PENDING' | 'APPROVED' | 'DECLINED' | 'VOIDED' | 'ERROR'` — **final states** are the
  four non-`PENDING` values; `PENDING` is the only pollable state.
- `TransactionAmounts = { productAmountInCents, baseFeeInCents, deliveryFeeInCents, totalInCents }` — the
  summary block; rendered exactly as received, never recomputed.

## API entity: PaymentRequest — `POST /transactions/:id/payment` body

| Field | Type | Rules |
|-------|------|-------|
| `cardToken` | string | single-use token from the 004 tokenization seam; memory-only |
| `installments` | integer | ≥ 1 (default `INSTALLMENTS_DEFAULT = 1`); shopper-chosen |
| `acceptedContracts` | literal `true` | both contracts accepted in the 004 form; server validates in the use case (`422 CONTRACTS_NOT_ACCEPTED` otherwise) |

## Request header: Idempotency-Key

| Field | Type | Rules |
|-------|------|-------|
| `Idempotency-Key` | string (header) | `16..64` chars matching `[A-Za-z0-9_-]` (`IDEMPOTENCY_KEY_PATTERN`); one per purchase attempt; generated by `ensureIdempotencyKey`, reused by every retry while the purchase is `PENDING`, sent only on `POST /transactions`; persisted in the recovery document so a reload replays instead of double-charging |

## State entity: CheckoutState (`features/checkout`) — unchanged shape, new lifecycle rules

The slice shape (`checkout.slice.ts`) is unchanged by this feature; what changes is **who resets it** and
**when** (Finalizar, 404-discard, summary→card-entry on restore).

| Field | Type | Rules |
|-------|------|-------|
| `currentStep` | `'product' \| 'cardAndDelivery' \| 'summary' \| 'finalStatus'` | flow step; **persisted**; `summary` is never restored (remapped to `cardAndDelivery` on reload) |
| `selectedProductId` | `string \| null` | **persisted**; validated against the API at startup |
| `quantity` | integer | 1–10; **persisted** |
| `delivery` | `DeliveryData \| null` | **persisted** (whitelisted keys only); deleted with the document at purchase end |
| `transactionId` | `string \| null` | **persisted**; pointer to the server-owned record |
| `idempotencyKey` | `string \| null` | **persisted**; `null` or 16–64 `[A-Za-z0-9_-]` |
| `cardBrand`, `cardLastFour` | `string \| null` | in-memory display only; **excluded from the whitelist** — these two are the *only* card-derived values allowed in Redux state; no card number/CVC field and no card token ever enters Redux (a dedicated test asserts the invariant) |
| `installments`, `contractsAccepted` | integer / boolean | in-memory; reset on restore and on Finalizar |
| `paymentStatus` | `PaymentStatus` | in-memory state machine; drives the in-flight lock (see below) |
| `paymentError` | `ApiError \| null` | serializable `{ kind, message }`, never `Error` |
| `transaction` | `TransactionView \| null` | latest server view, guarded |
| `lastReadRequestId` | `string \| null` | stale-read guard for concurrent status lookups |

### PaymentStatus state machine (client-side)

| Value | Meaning | Entered from |
|-------|---------|--------------|
| `idle` | nothing in flight | initial, restored, cleared error |
| `creating` | `createTransaction` in flight | Continuar |
| `paying` | `payTransaction` in flight | Pagar |
| `pending` | purchase exists, payment not final | 201/200 create, 202 pay, PENDING read; polling active |
| `approved` / `declined` / `voided` / `error` | terminal | a final `TransactionStatus` via `paymentStatusFromTransaction` |

The in-flight lock: Pagar/Continuar disabled while `paymentStatus ∈ { creating, paying, pending(polling) }`;
released by `transactionReceived` (success) or `paymentFailed`/timeout (error) — every terminal outcome
unlocks (US2.6).

## Persistence entity: Recovery Document (version 2, unchanged whitelist)

One document under localStorage key `checkout-progress`, written by the store subscriber
(`features/checkout/persistence.ts`). It is the *only* state that survives a reload, and it is a **pointer,
not a truth**: it can resume a journey but says nothing reliable about the payment outcome — on reload the
**server** (`GET /transactions/:id`) is the single source of truth for the recovery/transaction status,
and the persisted fields only tell the app *what to look up* (`transactionId`) and *with what* (`idempotencyKey`).

| Field | Type | Rules |
|-------|------|-------|
| `version` | integer | must equal `PERSISTENCE_VERSION = 2`; anything else → discard (FR-012) |
| `savedAt` | ISO 8601 string | refreshed per write; `now − savedAt > 24 h` → discard |
| `currentStep` | `CheckoutStep` | unknown value → discard; `summary` restores **as** `cardAndDelivery` (FR-014) |
| `selectedProductId` | `string \| null` | validated asynchronously; `notFound` discards all progress |
| `quantity` | integer | 1–10; otherwise discard |
| `delivery` | object \| null | whitelisted keys `fullName, email, phone, address, city, region, notes` only |
| `transactionId` | `string \| null` | non-sensitive reference; triggers the reload lookup (spec FR-010) |
| `idempotencyKey` | `string \| null` | `null` or 16–64 of `[A-Za-z0-9_-]`; anything else → discard |

Unknown keys are ignored on read and never written; the serialized-document test asserts no card-like key
(`card`, `cardNumber`, `cvc`, `cvv`, `pan`, `expiry`, `expiration`, `securityCode`) ever appears.

## Recovery-document lifecycle (this feature)

```text
create (subscriber write) ──▶ persisted document (version 2)
        │ reload
        ▼
validate shape/version/staleness ── invalid/stale ──▶ discard, clean start
        │ valid
        ▼
validate product (fetchProduct) ── notFound ──▶ discard (startOver)
        │ ok, transactionId present
        ▼
GET /transactions/:id (server = truth)
   ├─ 200 PENDING  ──▶ finalStatus + resume polling (same 2 s / 40 s budget)
   ├─ 200 final    ──▶ finalStatus with that outcome (no polling)
   ├─ 404          ──▶ discard document, clean start (FR-011)
   └─ transient (network/429/503) ──▶ recovery error + retry, document KEPT

Finalizar ──▶ remove document + startOver + navigate to product page + fresh product fetch
```

### Discard / clear triggers (consolidated)

| Trigger | Source | Effect |
|---------|--------|--------|
| Version ≠ 2, invalid JSON/shape, bad key, stale > 24 h | loader (003 rules, FR-012) | remove document, preload empty |
| Selected product `notFound` on startup validation | `restoreProgress` | remove document, `startOver` |
| Reload lookup `404 TRANSACTION_NOT_FOUND` | `readTransactionStatus` (FR-011) | remove document, `startOver` |
| Shopper chooses start over | existing UI | remove document, `startOver` |
| **Finalizar** on a terminal status screen | `finalizeCheckout` (FR-015) | remove document, `startOver`, navigate + refetch |
| Storage corrupted/unreadable | loader `try/catch` | treated as absent |

### Step transitions (new/changed)

| From | Trigger | To |
|------|---------|----|
| `cardAndDelivery` | Continuar → `createTransaction` success | `summary` |
| `summary` | Pagar → pay accepted (202/200) | `finalStatus` |
| `summary` | reload | **`cardAndDelivery`** (never restored directly; FR-014) |
| `finalStatus` | lookup/poll reaches final status | `finalStatus` (terminal view + Finalizar) |
| `finalStatus` | Finalizar | `product` (all progress cleared) |
