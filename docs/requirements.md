# Checkout Onboarding: Requirements (source of truth)

> This document is the input for the Constitution and for every `/speckit-specify` run.
> Feature specs generated by spec-kit live in `specs/NNN-*/`. This file never contains secrets.

## 1. Goal

Build a mobile-first checkout for a tech-accessories store: a customer picks a product, enters
(fake) credit card and delivery data, reviews a payment summary, pays through a payment provider
**sandbox**, sees the result, and returns to the product page with the stock updated.

Quality attributes evaluated: code clarity, API/endpoint design, design simplicity, test coverage,
correct HTTP usage, UI quality, data management, infrastructure as code, software principles and
supervised use of AI as a coding assistant.

## 2. Business flow (5 screens)

| # | Screen | Purpose |
|---|--------|---------|
| 1 | Product page | Show product(s): image, name, description, price, units in stock. Button "Pay with credit card". |
| 2 | Card + delivery modal | Collect and validate card data and delivery data. |
| 3 | Summary (backdrop) | Product amount + fixed base fee + delivery fee, with the pay button inside a backdrop component. |
| 4 | Final status | Show the transaction result (approved / declined / error). |
| 5 | Product page | Redirect back with the stock already updated. |

## 3. Functional requirements

- **FR-1** Product page lists seeded products with units available. Out-of-stock products cannot be bought.
- **FR-2** "Pay with credit card" opens a modal.
- **FR-3** Card form with validation: number (Luhn, length), brand detection with VISA / MasterCard logos
  (bonus), expiry (not in the past), CVC, cardholder name. Test card data only.
- **FR-4** Delivery form: full name, email, phone, address, city, region, optional notes. Validated.
- **FR-5** Summary shows product amount, base fee (always added) and delivery fee. Fees are configurable constants.
- **FR-6** On pay: (1) create a `PENDING` transaction in our API and get its number; (2) call the payment provider;
  (3) when it finishes (approved or not): update the transaction with the result, assign the product to the
  customer's delivery (only when approved), and update stock.
- **FR-7** Show the final result, then redirect to the product page with refreshed stock.
- **FR-8** Resilience: if the page is refreshed at any step, the app restores the progress (step, product, delivery
  data, transaction id) and asks the backend for the real transaction status.

## 4. Domain and data model

Entities (all required by the brief): **Product (with stock)**, **Customer**, **Transaction**, **Delivery**.

- Money is stored as integers in minor units; currency COP.
- Transaction status enum: `PENDING`, `APPROVED`, `DECLINED`, `VOIDED`, `ERROR`.
- Each transaction has a unique `reference` and an idempotency key.
- DB constraints: `stock >= 0` (CHECK in a SQL migration), unique keys, foreign keys, enums.
- Seed: 8 to 10 tech-accessory products with small WebP images.
- The data model diagram goes in the README.

## 5. API (indicative, final contract decided in the plan and documented in Swagger)

| Method | Path | Notes |
|--------|------|-------|
| GET | `/products`, `/products/:id` | Includes available stock |
| POST | `/transactions` | Creates the `PENDING` transaction, customer and delivery data; returns id and reference. Honors `Idempotency-Key`. |
| POST | `/transactions/:id/payment` | Backend calls the provider with the card token and finalizes the transaction |
| GET | `/transactions/:id` | Source of truth for the status (used after refresh) |
| POST | `/webhooks/payment-events` | Optional: provider events, signature verified |

Correct HTTP usage: proper verbs, status codes (201, 400, 404, 409, 422), consistent error body.

Validations to define per endpoint include: product exists, quantity > 0, enough stock, valid customer and
delivery fields, transaction is still `PENDING`, no double payment of the same transaction, token present,
idempotent retries.

## 6. Payment provider integration (sandbox only)

- Always use the sandbox environment and the sandbox keys. No real money.
- The browser tokenizes the card directly with the provider's **public key**. The back-end never receives
  card number or CVC.
- The back-end uses the private key and integrity secret server-side only (integrity signature, acceptance
  token and other fields as required by the provider docs; verify exact fields during the plan).
- The provider can answer `PENDING` first: the back-end polls the status with a timeout (and/or handles the
  webhook) until a final state.
- Keys live in environment variables. Commit a `.env.example` with empty values, never the real ones.

## 7. Frontend

- React SPA (no other frameworks, no Next.js), TypeScript, Vite.
- **Redux Toolkit** following Flux: slices (product, checkout, delivery, transaction), thunks for async calls.
- Persist only a whitelist of non-sensitive state: current step, selected product, delivery data, transaction
  id/reference/status. **Never** card number or CVC in Redux persist or localStorage.
- Tailwind CSS, flexbox/grid. Mobile-first. Reference minimum device: iPhone SE (2020), 375x667 CSS px
  (750x1334 physical pixels). No horizontal overflow, nothing outside the UI boundaries.
- Fast images: WebP, explicit width/height, lazy loading below the fold.
- Works in the main browsers (bonus: fully responsive).

## 8. Backend

- NestJS + TypeScript, PostgreSQL, Prisma.
- **Hexagonal architecture (ports and adapters)**: `domain/` (entities, value objects, ports),
  `application/` (use cases), `infrastructure/` (Prisma repositories, payment gateway adapter, HTTP).
- Controllers contain no business logic. Use cases never import `PrismaClient` or the provider SDK.
- Use cases follow **Railway Oriented Programming** with a typed `Result`; business errors are values, not exceptions.
- Validation in three levels: DTOs (`class-validator`), domain/use-case rules, database constraints.
- Stock changes are atomic and conditional (decrement only if `stock >= quantity`) inside a Prisma transaction.

## 9. Security

- Card data never reaches or lives in our systems. Secrets only in env vars.
- OWASP alignment: input validation, safe error messages, rate limiting, CORS restricted, security headers
  (e.g. Helmet), HTTPS in deployment, dependency audit. Check the deployed site with a headers scanner.

## 10. Testing

- Jest in back-end and front-end, **coverage above 80%** in each, report included in the README.
- Back-end use cases tested with in-memory fakes of the ports (no database needed).
- Front-end: reducers/thunks, validators (Luhn, brand detection), key components and the restore-after-refresh logic.

## 11. Deployment and infrastructure as code

- Dockerfile per app and a `docker-compose` for local development.
- Publish on a cloud provider (AWS recommended: e.g. ECS/App Runner + RDS + S3/CloudFront) with a minimal
  Terraform or CDK. If Railway is used, Dockerfiles and compose must be clearly documented.
- Public URLs for the front-end and the Swagger/Postman collection go in the README.

## 12. Repository and workflow

- Public GitHub monorepo: `back-end/`, `front-end/`, `docs/`, `specs/`, `.specify/`.
- Do **not** use the payment provider's company name anywhere in the repository (names, files, docs, code).
  Use generic names such as `PaymentGateway`.
- One branch and one pull request per feature. Spec-kit feature branches keep their numbered names.
- Conventional Commits (`feat`, `fix`, `test`, `docs`, `chore`, `refactor`, `ci`), small and frequent.
  Visible commit history is required.
- README must contain: overview, architecture, data model, API docs link, how to run, test coverage results,
  deployment links, security notes, and the AI/spec-driven workflow used.

## 13. Evaluation priorities

Base (100): README 5, images and UI boundaries 5, full checkout flow 20, API 20, **tests above 80% 30**,
deployment 20. Bonus (50): OWASP/HTTPS/headers 5, responsive and cross-browser 5, CSS 10, clean code 10,
hexagonal 10, ROP 10. At least 100 points are needed, so bonuses are the safety margin.

## 14. Edge cases checklist

Out of stock at payment time; two buyers for the last unit; double click on pay; refresh in the middle of
payment; provider timeout or `PENDING`; declined card; invalid or expired token; provider unavailable;
retry with the same idempotency key; amount tampering (always recompute the amount on the server).

## 15. Development loop (per feature)

1. `/speckit-specify` (creates the numbered branch) and clarify open questions.
2. `/speckit-plan`, `/speckit-tasks`, optional checklist and consistency analysis before coding.
3. `/speckit-implement` in small commits; tests written with the code.
4. `/speckit-converge`; repeat implement and converge until it reports **Converged**.
5. Definition of done: tests green, coverage still above 80% for touched code, lint and type-check clean,
   README and Swagger updated, no secrets, no provider company name, PR opened with a short summary and merged.

Command names may differ by spec-kit version; use what the agent exposes.

## 16. Feature roadmap (one spec each, in order)

1. **Back-end base**: hexagonal modules, Prisma schema, CHECK migration, seed, `GET /products`.
2. **Transactions**: create `PENDING`, gateway adapter, finalize, delivery assignment, atomic stock.
3. **Front-end base**: Redux Toolkit store, product page with stock.
4. **Card and delivery modal**: validation, brand logos, tokenization.
5. **Summary backdrop, final status and refresh recovery.**
6. **Deployment, IaC, Swagger/Postman and README with coverage.**

## 17. Decisions and assumptions (revisit in the plan)

- D1: Stock is reserved with a conditional decrement when the `PENDING` transaction is created, and released if
  the payment ends declined, voided or error. This avoids overselling and still ends with the stock updated.
- D2: Guest checkout, no customer authentication.
- D3: Single monorepo, back-end tests with Jest (CommonJS).
- D4: Base fee and delivery fee are configurable constants; exact values chosen in the plan.
